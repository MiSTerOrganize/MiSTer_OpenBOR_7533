# Tier-B adversarial review round 1 — 2026-07-30

Four independent reviewers over the Phase 0 / 0b / 1 / 1b work. **Verdict: the design is
NOT ready for Phase 2.** 8 CRITICAL + 18 MAJOR architecture defects, 15 numeric findings,
7 engine-fact corrections. Two CRITICALs are go/no-go for the whole approach.

Ordered by what has to be settled first.

---

## GO/NO-GO — settle these before any further Phase work

### C2 — The sprite arena is UNCACHED, and that may invert the entire payoff
§6 has the ARM `mmap` the arena "exactly as `native_video_writer.c` does" — i.e.
`/dev/mem` + `O_SYNC` + `MAP_SHARED` = **strongly-ordered, uncached**. Today that is
tolerable because the traffic is *write-only streaming* (143 KB/frame). After Tier-B the CPU
**reads** sprite RLE + palettes out of that arena for the 29% fallback, and writes ~1 MB/frame
of fallback scratch — all uncached. Uncached random reads on the A9 are ~10–40x slower than
L2-resident. The f2h ports are **not coherent** with A9 L1/L2 and ARMv7 userspace cannot
issue cache maintenance, so a cached mapping would silently feed the FPGA stale bytes.
**Action: measure an uncached-read `gfx_draw_scale` on the A9 before anything else.**
If it is as slow as feared, either the fallback rasterises from a cached shadow copy (which
destroys the "relocation, not duplication" RAM claim), or the arena idea dies.

### C3 — "The ARM never reads back composited pixels" is FALSE
`patches/pausemenu_patch.c:66-73` does `copyscreen(pausebuffer, vscreen)` then
`spriteq_draw(pausebuffer,…)`. With compositing on the FPGA, `vscreen` is never composited →
**black pause snapshot**, the exact failure CLAUDE.md already records for the PIXEL_32
pausebuffer. Same class: `backto_mainmenu`, the `getscreen()` script API, screenshots,
`blendscreen`/fade transitions, the anigif cutscene path.
**Action: enumerate every destination-read site and define an explicit "ARM owns the
framebuffer this frame" handoff** — or budget reading the composited band back, which the
bandwidth model does not include.

## CRITICAL

### C1 — No DDR3 arbitration exists, and the current reader cannot tolerate a second master
`OpenBOR.sv:492-497` is a *static* mux onto ONE 64-bit port (`ram1`). The compositor needs
sprite reads + framebuffer writes on that same port. `openbor_video_reader.sv:345` captures
beats with `if (state == ST_WAIT_LINE && ddr_dout_ready)` — Avalon reads carry **no ID**, so
any compositor read in flight during a scanline read is latched into the line FIFO as pixels
and `beat_count` desyncs. **The doc has no port-ownership section at all.**

### C4 — §9.5 does not describe the shipped downscaler; byte-identity fails on ~18 of 20 resolutions
`native_video_writer.c` `bpp==16` has **four** width-selected implementations:
- `width==320` (**286 PAKs**) → NEON **swap-only, NO box**, row via `src_y=(y*sy256)/256`
  (doubly-truncated NN, ≠ `floor(y*H/224)`; at 320x240 y=112 shipped picks row **119**, the
  doc's formula gives **120**).
- `width==960` → 3x box. `width==640` → 2x box.
- `width==480` (**94 PAKs**) → 3:2 box with **per-parity hcnt** and two reciprocals.
- everything else → scalar box, **per-column** `hcnt = x1-x0`.
The doc's `hcnt = src_w/out_w` is constant and only correct for 960 and 640; for widths
<320 it yields `hcnt = 0`. The 320 NEON branch is also gated on source 16-byte alignment,
which the FPGA cannot observe.

### C5 — One `pal_addr` per command cannot express the LOCKED v3.10 dual-flag discriminator
`apply_patches.py:5437`:
`table_arg16 = (frame && frame->palette && drawmethod->has_remap_directive && !drawmethod->has_palette_directive) ? NULL : drawmethod->table;`
ATOV-class uses `frame->palette`; TMNT-RP/modern use `drawmethod->table`. §5 speaks as if the
sprite's own palette is always right. **Shipping that re-introduces the months-long ATOV /
TMNT-RP palette regression architecturally.** The ARM must evaluate the same expression and
emit the *effective* palette address; both flags join the offload gate.

### C6 — No compositor→scanout handshake; the sequence number signals the wrong event
`reader.sv:526` treats any `ctrl_word[31:2]` change as "a fully written frame exists". Under
Tier-B the ARM's sequence number means "a display list is ready" — *before* compositing. The
reader would scan out a buffer the compositor is still writing. Framebuffer-valid must be a
compositor-owned signal; the DDR3 sequence number must gate the **compositor**, never scanout.

### C7 — "2 slots + the ARM never waits" is a contradiction
If the FPGA misses a frame, the ARM at N+1 must stall (the thing Tier-B removes) or overwrite
the slot being read (corruption, and the fetch engine follows `src_addr` into reused memory).
Pick: 3+ slots with drop-oldest, or explicit frame-drop. Same for the 2 MB scratch.

### C8 — The fetch engine has no bound or timeout
§9.2 exits a row only on `0xFF`. If arena content changed underneath (model unload, PAK load,
hot-swap, `.s1` replay reset) the stream is arbitrary and `0xFF` may never appear. The
existing reader guards every wait state with `TIMEOUT_MAX`; the new block inherits none.

## MAJOR (selected — full list in the session record)

- **M2 — a gate that offloads something NOT identical.** `getblendfunction16` also depends on
  globals `tintmode` and `usechannel`; both are script-mutable per sprite. "mode outside 1..6
  → CPU" passes a tinted sprite to the FPGA, which renders the plain mode.
- **M4 — blended fallbacks cannot be LINEAR.** Rasterising standalone into scratch loses the
  destination operand. Water *displaces destination content* and is not a source rasterisation
  at all. "Z-order is exact" holds only for **opaque** fallbacks.
- **M1 — the band formula drops the shipped clamps** (`if(yy1<=yy0) yy1=yy0+1;` etc). For
  `H < 224` (240x200, 240x224, 256x224, 384x224) the last output row of band *k* can need the
  first source row of band *k+1*. "Exact by construction" is unproven.
- **M6 — command volume priced against one PAK again.** He-Man is 15 bands not 4, Lust Rush
  56; the background LINEAR is per-band. 128 KB / 32 B / 2 = **2,048 commands/frame** ceiling
  with no overflow policy.
- **M7 — the encoding cannot express variable band geometry.** One global `band_height` in the
  header; §8.2 says source lines vary ±1 and claims a per-band parameter that **does not exist**
  in §7.1/§7.2.
- **M9 — clipping must not skip bytes.** Always consume every row to `0xFF`; clipping
  suppresses *writes* only, or the stream desyncs.
- **M12 — the CDC table is cargo-culted.** The row flagged as the Option Y trap is not a pulse
  crossing at all; the crossings that genuinely exist are unlisted.
- **M13 — ">= 2 px/clock" unsubstantiated for blends** (read-modify-write needs 2 reads AND 2
  writes/cycle; forces banking that collides with arbitrary-`dst_x` RLE runs).
- **M14 — the golden-trace gate as written cannot pass or cannot mean anything** (+1 frame of
  latency re-indexes `FRAME:` for every comparison).
- **M16 — §9.4 freezes blend scope from three PAKs.** The one-example fallacy the doc's own
  lesson list forbids. Run the histogram over the 431-PAK corpus.
- **M18 — a 4th PLL output is not free**: regenerating `pll.v` re-rolls placement on a design
  whose worst path is +0.128 ns, and `OpenBOR.sdc` matches counter names by literal string.

## ENGINE-FACT CORRECTIONS (verified against pristine v7533)

### E1 — 🛑 My census correction #5 was WRONG; the original checklist was right
`Ultimate Super Mega Beatdown` bundles a third-party tool tree. My scanner's
`endswith("data/video.txt")` matched the nested
`DATA\OPENBORSTATSV051\TOOLS\OBOR\DATA\VIDEO.TXT` (= `video = 1`) **before** the real
`DATA\VIDEO.TXT` (= `video 1` → **480x272**). The engine matches the name exactly via
`List_GetNodeByName`.
**Consequences: 446/450 not 445/450; 4 corrections not 5; 480x272 = 98 not 97;
320x240 = 282 not 283. The `video = 1` trap loses its only witness** (the behaviour is real,
no PAK demonstrably exercises it). Band-geometry `R` values unchanged.

### E2 — `data/videopc.txt` is checked FIRST on LINUX builds and my scanner never looks at it
`openbor.c:48567` `tryfile("data/videopc.txt")` **replaces** `data/video.txt`, and our build
defines LINUX. One PAK ships it (Super Fightin' Spirit, same value, so no census change today)
— but the scanner is not engine-exact as claimed.

### E3 — 🛑 SHADOWS CAN NEVER REACH THE FAST PATH, so the "MULTIPLY is mandatory" reasoning is void
`openbor.c:29711` `shadowmethod.scaley = light.y * scaley / 256` with `light.y` default **64**
→ `scaley != 256` → the gate fails. Independently `:29705` sets
`shadowmethod.fillcolor = shadowcolor` (non-zero required) → also fails. **Shadows are 100%
`gfx_draw_scale`.**
The measured data stands (140 PAKs ran MULTIPLY at the gate without declaring it) but **my
explanation for it was wrong and the cause is now UNKNOWN.** Re-investigate before using
MULTIPLY frequency to justify anything.

### E4 — Model loading is a `load`/`know` MIX, not "on demand"
`load_models()` eagerly loads every cache entry with `loadflag` set (models.txt **`load`**);
only **`know`** models are demand-loaded. The lower-bound conclusion survives, but the gap is
**PAK-dependent, not uniform**. Shrink path confirmed (`unload_level` → `cache_model_sprites(m,0)`
/ `free_model`), so the free/reuse allocator requirement stands.

### E5 — `s_sprite` has 12 header fields, not the 8 the doc lists
Missing `offsetx, offsety, srcwidth, srcheight`. `data[]` starts at **byte 48** on arm32, not
32 — load-bearing for the ARM's `linetab` seek, in the section that says "do not re-derive
this from memory".

### E6 — The fallback has four destinations, not one
`gfx_draw_plane` / `gfx_draw_water` / `gfx_draw_rotate` / `gfx_draw_scale`.

### E7 — tint and usechannel are mutually exclusive (`if` / `else if`), not independent.

**Confirmed correct:** the RLE format (self-relative `linetab`, contiguous rows, 0xFF EOL,
0xFE/0xFF caps, TRANSPARENT_IDX 0), `getblendfunction16` semantics and the missing bounds
check on `alpha>6`, the preset table and last-wins loop, `ParseArgs` termination, the God of
War `#`-before-`x` trap **verified against the real bytes**, the packfile directory format,
and the fast-path gate condition verbatim.

## TOOLING DEFECTS (4th reviewer) -- these invalidate published measurements

### T1 -- CRITICAL: the blend census and overdraw SILENTLY EXCLUDE the slow path
The probe increments the histogram only INSIDE the fast-path branch, but `analyze` divides
fast-path-only pixels by the FULL-run `vw*vh*frames`. **253,871 of 2,147,759 blits (11.8%)
are slow, across 186 PAKs**, and they contribute no mode and no pixel.

| PAK | slow% | published overdraw | corrected |
|---|---:|---:|---:|
| Memory Loss | 92.3% | 0.13x | ~1.74x |
| Quack Ninja | 78.4% | 1.31x | ~6.05x |
| Ninja - Stealth Assassins | 7.5% | 38.56x | ~41.67x |

The published **median 1.05x / mean 1.99x overdraw -- the figure the DDR3 budget is sized
from -- is understated by up to 13x per PAK.** Worse: scaled/rotated/water sprites are exactly
the ones most likely to carry a blend mode, and they are structurally invisible to the census.

### T2 -- CRITICAL: same `endswith` bug the engine-fact reviewer found, independently
Two reviewers with different methods converged on `Ultimate Super Mega Beatdown`. See E1.
Fix is `name == "data/video.txt"`.

### T3 -- HIGH: the sprite "CEILING" is not a ceiling
`IMG_EXT = (.gif,.png)` but `loadimg.c:1236-1251` also dispatches **`.pcx` and `.bmp`**.
**13,701 excluded images = 883.8 MB in 146 PAKs**; Marvel War of the Gems is **+116%**
(220.8 -> 476.2 MB). The aggregate conclusion survives (library total +0.9%) but the
per-PAK "if it fits this, it fits" guarantee does not.

### T4 -- HIGH: one TSV line mixes two measurement windows
The 5-second dump resets `m*/p*/tint/chan/remap` but NOT `fast/slow/frames/spritekb`.
Detector `sum(m0..m7) != fast` fires on **1 PAK today** (The Suffering In Me, 43% coverage)
and on everyone at higher `OB_FRAMES`. `analyze` has no such gate.

### T5 -- HIGH: `_mister_tbb_px[]` is uint32 and is at **63.6% of UINT32_MAX**
Max observed 2,733,254,549 (Ninja - Stealth Assassins) at OB_FRAMES=900; 3 PAKs above 50%.
`OB_FRAMES=1800` wraps. A wrap makes the sum SMALL, so it reports a **low** overdraw --
plausible and wrong in the dangerous direction.

### T6..T9 -- MEDIUM
19,372 zero-pixel calls skew %calls vs %px (MULTIPLY 8.4% -> 7.6%); `pak_blendscan.py`
misses the `changeentityproperty(ent,"alpha",N)` bridge (**70 hits in 21 PAKs, 10 of them
with no other bridge**); the scan driver's per-job `HOME` isolation **is a no-op** (the MiSTer
patches rewrite to absolute `/media/fat/...`, so all workers shared one log and config); and
several unchecked `cp`/`apt-get` paths would yield 450 valid-looking title-screen histograms
if `ai_menu_start.txt` went missing, with nothing flagging it.

### Checked and CLEAN (do not "fix")
Packfile directory handling is engine-exact (0 truncated walks, 0 duplicate names across
450); GIF header offsets match `opengif`; the 1,453 non-GIF `.gif` files are correctly
skipped (1,387 are macOS `._*` forks); `RE_MODEL_ALPHA` does not over-match; `RE_DM_POS`
picks the right argument; no parallelism corruption in this run.

## What this means

Phase 1b (blend histogram) does not touch C1–C8. **Settle C2 and C3 first** — either can
invalidate the architecture. Then C4/C5, without which the byte-identity and no-regression
contracts are unmeetable as specified.
